# Decisions

| # | Decision | Why |
| --- | --- | --- |
| 1 | Seeded accounts with email + password, no signup, no SMTP | Internal first; avoids email deliverability work; admin controls who joins |
| 2 | Members cannot write tables directly; writes via server actions / `submit_answer` | RLS cannot restrict columns; keeps time and locks server-side |
| 3 | Final answer locked after first submit; steps editable until close | Stops gaming speed points and brute-forcing the auto-check |
| 4 | Speed measured from first submit | Safe because the final answer is locked |
| 5 | Grading after close, no deadline | Removes edit-after-grade races |
| 6 | Mark scheme as structured criteria; steps bonus = ticked criteria sum | Consistent grading across 2-3 admins, faster |
| 7 | Guests see results only after close | Stops members guessing logged out before submitting |
| 8 | Guests store nothing | Less student-data risk |
| 9 | Polling instead of Realtime | Realtime does not stream views; grade RLS would block events |
| 10 | No Redis / rate-limit store for now | About 40 members; Supabase Auth limits cover login; the guest check reveals the answer after close anyway. In-memory counters do not work on serverless, so add Upstash or a Postgres counter table only if abuse appears |
| 11 | Admins excluded from the leaderboard | They see answer keys |
| 12 | LaTeX authoring with placeholder toolbar + live preview | Admins type formulas; students use photos for steps |
| 13 | Two Supabase projects (staging, prod) | Previews must never touch production data |
| 14 | `release_at`/`closes_at` generated from `release_date` | Windows cannot overlap; warn about gaps instead |
| 15 | Any unique email works as the login identifier | Supabase needs an email-format identifier but never delivers mail to it; students without a school email can still join |
| 16 | Login goes through a server action | Supabase Auth's built-in rate limit then applies to every attempt |
| 17 | `must_change_password` mirrored in `app_metadata` | Middleware reads it from the JWT with no DB query; users cannot edit `app_metadata`; `changePassword` clears it |
| 18 | Name and class are admin-managed; members have no write on `profiles` | Keeps leaderboard names trustworthy and the RLS surface smaller |
| 19 | No attempt cap for guests | The key is revealed after close anyway. If instant feedback is wanted later: 3 attempts per question per IP, accepting that incognito bypasses it |
| 20 | Reminders go through the club WhatsApp group, not push | PWA push and in-app notifications are out of scope for v1 |
| 21 | Brand accent colour is deep navy `#0B1F4D` | The client's colour theme; palette and contrast checks in `docs/UI_GUIDE.md` |
| 22 | No client write policies at all: `anon` and `authenticated` are read-only on every table, admins included. Admin writes use the service role inside server actions | RLS cannot restrict columns; an UPDATE also needs a SELECT policy, and `question_keys`/`question_markschemes` deliberately have no client SELECT, so an admin write policy there could never work. One write path per table is easier to audit than a policy per role |
| 23 | **Superseded by 30.** Originally: `submit_answer` takes `p_auto_verdict` from the server action, which computes it with `lib/answers.ts` | The first half of the reasoning was right — one normaliser, not two. The second half was wrong: I claimed a forged verdict "buys nothing" because it only pre-fills the admin's screen. It buys a lot. The grader's `C`/`Enter` shortcut (R-4) accepts that pre-fill, and points follow `is_correct`, so a member who called the RPC directly with `p_auto_verdict: 'correct'` could get base + speed points for a wrong answer. Caught by the security reviewer, not by me |
| 30 | `submit_answer` is callable only by `service_role` and takes an explicit `p_user_id`; the verdict is never accepted from a member-held token | Closes the hole in 23. The member path can no longer reach the function at all (`revoke execute from public, anon, authenticated`), so `p_auto_verdict` is only ever set by the trusted server action that compared the answer against `question_keys` with `lib/answers.ts`. `lib/answers.ts` stays the single normaliser instead of being duplicated into SQL. `user_id` comes from the verified session in the action rather than `auth.uid()`, which is exactly the "writes go through server actions" model of hard rule 1 and decision 22. Atomicity (M-5), the DB clock and the final-answer lock (M-3) are unchanged, and the RLS suite now pins the stronger property: a member calling the RPC gets 42501 |
| 24 | `proxy.ts` (Next 16's renamed middleware) is an optimistic gate only — guests out of private routes, `must_change_password` to `/ganti-sandi`. The role check lives in `requireAdmin()`, a database read through RLS | A JWT claim can be up to an hour stale, so it must never be the only thing guarding the answer keys. Reading `must_change_password` from `app_metadata` still avoids a query on the common path (decision 17) |
| 25 | `enable_signup = false` and `minimum_password_length = 8` in `supabase/config.toml` | Local must behave like the hosted projects, otherwise the "public signups are rejected" RLS test passes locally for the wrong reason and A-3's 8-character floor is not actually enforced |
| 26 | The four UI bundles share one working tree under strictly disjoint file ownership, instead of one git worktree each | A fresh worktree has no `node_modules` and no generated `.next/types`, so every agent would need a full install plus a typegen before `pnpm typecheck` could run — real cost on a one-day deadline. The file sets do not overlap, so same-tree parallel work is safe. Trade-off accepted: an agent that strays outside its list could disturb another, which the briefs forbid explicitly |
| 27 | The guest answer check ships in bundle C (the Today page), not bundle D | It lives on `/`, which bundle C owns. Splitting it out would have forced a cross-bundle import and left both agents with a failing typecheck for the whole phase |
| 28 | One markdown renderer only: `components/math/math-markdown.tsx`. `components/today/markdown.tsx` and `components/latex/math-markdown.tsx` are re-export shims | Bundles B and C each wrote a Markdown+KaTeX wrapper. Both correctly omitted `rehype-raw`, but two copies means the admin preview and the member page can drift, and a future `rehype-raw` in one of them would silently break hard rule 6. The merged version keeps B's component map (safe link `rel`/`target`) and C's mobile overflow handling (only `.katex-display` scrolls, so a long formula never widens the page) |
| 29 | `experimental.serverActions.bodySizeLimit = '10mb'` | The admin question-image upload goes through a Server Action and the bucket allows 8 MB, but the action body defaults to 1 MB, so any real image failed before the action ran. Member step photos are unaffected: the browser uploads them straight to Storage and only paths are submitted |
| 31 | `await connection()` before reading the clock in `components/today/data.ts` | `cacheComponents` makes an unmarked `new Date()` in a server component fail at request time ("Next.js encountered the unstable value `new Date()` while prerendering") and `/` rendered nothing but its skeleton. The production build did NOT catch this — only a real request does — so `pnpm build` alone is not sufficient verification for this route. The value is display-only (S-4 countdown correction); whether the question is open is still decided by Postgres |
| 32 | The `/nope`-style unknown path returns 307 to `/login` for a guest instead of 404 | `proxy.ts` gates everything outside `/`, `/login` and `/arsip` before routing, so it cannot tell a typo from a private page. Harmless (the login page is a fine landing spot and the real 404 shows once signed in), but noted so it is not mistaken for a bug later |
| 33 | SPEC M-6 now reads `Terkirim (HH.MM WIB)`; the code was already right | The app renders `04.00` because that is the Indonesian convention and because S-3's sentence already renders the release time that way (`pukul 04.00 WIB`). M-6's `HH:MM` was the odd one out — the spec was wrong, not the chip. Caught by the spec reviewer as a deviation; fixing the spec rather than the copy keeps the two times on screen consistent with each other |
| 34 | `submissions.auto_verdict` is protected by a column-level grant, not by RLS | RLS filters rows, never columns, and PostgREST exposes every column of a row the policies allow, so a member could read their own pre-fill verdict while the question was still open — a genuine M-7 violation, reproduced over HTTP with a real member JWT (`auto_verdict values a member can read: ["correct"]`). `authenticated` is now granted SELECT on every column except `auto_verdict`, so `select auto_verdict` and `select *` both fail with 42501. Hard rule 2 says sensitive data belongs in its own table; moving the verdict would mean migrating the grading flow, so the grant layer carries it for now. Consequence, and the part that bit us: column grants are role-based, so this covers admins too — `lib/actions/grading.ts`'s roster loader had to switch to the service-role client, and every future verdict read must do the same |
| 35 | The pgTAP suite passing does not mean the app works | Decision 34 is the worked example: the suite went green at 261 assertions while the grading queue was broken at runtime, because the suite pins the database property and cannot see which Supabase client the app used. Both real regressions this round (`/` failing to prerender, and this) were found by running the thing, not by running the tests. Budget time for a runtime pass |
| 36 | The login form carries `method="post"` | Found by driving the page: a submit that lands before React hydrates is a native form submission, and with no `method` the browser does a GET, so the email and the password went into the URL, the browser history and the access log. `method="post"` makes the no-JS path a 405 that leaks nothing. The app still needs JS to sign in, so nothing is lost |
| 37 | `scripts/seed.ts` takes `SEED_PROFILE=demo\|starter\|admins` instead of a boolean | A boolean (`SEED_ONLY_ADMINS`) could not express the launch shape: one admin, one real question, no students. `demo` keeps the old full fixture set for local work, `starter` is the launch shape, `admins` is production. The old variable is still accepted as an alias so `docs/RUNBOOK.md` links in the wild keep working. Admins seeded from `SEED_ADMIN_PASSWORD` are no longer forced to change it — the operator chose that password, unlike a generated member one |
